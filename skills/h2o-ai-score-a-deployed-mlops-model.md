# Score a model deployed through H2O MLOps

The H2O MLOps Scoring REST API is the runtime surface of one deployed model. It is a small,
seven-operation contract, and it is deliberately self-describing: you can discover the exact
input shape from the endpoint itself before you send anything.

## Resolve the host first

The published specification declares `servers: [{ url: "https://{defaultHost}" }]` with the
variable defaulting to `www.example.com`. **That is a placeholder, not a host.** Every
deployment gets its own endpoint, assigned by H2O MLOps at deploy time. Get the real URL from
the MLOps UI or from the `h2o-mlops` Python client (`pip install h2o-mlops`,
<https://docs.h2o.ai/mlops/py-client/overview>) before calling anything here.

The specification also declares no `securitySchemes` even though every operation declares a
`401` response — so the authentication mechanism has to come from the deployment
configuration, not from the contract.

## Steps

1. **Confirm you are talking to the model you think you are —
   `model_id_model_id_get`** (`GET /model/id`). Returns the unique id of the model loaded in
   the scoring server. Assert this against the model you intended to call. Endpoints get
   re-pointed; ids do not lie.

2. **Discover the input contract — `model_schema_model_schema_get`**
   (`GET /model/schema`). Returns the model's input and output fields with their data types.
   Build your request from this, not from a schema you cached at integration time — a
   redeployed model can change its columns.

3. **Get a worked example — `sample_request_model_sample_request_get`**
   (`GET /model/sample_request`). Returns a valid sample request body for this model. This is
   the fastest way to get a first call right, and the only "test fixture" H2O.ai publishes
   anywhere in its API surface. Note it can return `501` when the deployment does not
   implement it.

4. **Check what the endpoint supports —
   `capabilities_model_capabilities_get`** (`GET /model/capabilities`). Returns the scoring
   capability list. Call this *before* attempting media scoring or contributions — both are
   optional and both return `501 Not Implemented` on deployments that lack them.

5. **Score — `score_rows_model_score_post`** (`POST /model/score`).
   Takes a `ScoreRequest` (fields plus rows) and returns a `ScoreResponse`. Batch rows into
   one request rather than one request per row.
   For image or audio models use `score_media_model_media_score_post`
   (`POST /model/media-score`), which takes a multipart body.

6. **Explain the prediction —
   `score_contributions_model_contribution_post`** (`POST /model/contribution`).
   Takes a `ContributionsRequest` and returns per-feature Shapley values, optionally grouped.
   This is the operation to reach for when a decision needs to be justified to a human or an
   auditor — it is the model's own attribution, not a post-hoc guess.

## Rules

- **Handle `501` as a normal outcome, not a bug.** `sample_request`, `capabilities`,
  `media-score`, `score` and `contribution` all declare `501` — deployments legitimately
  differ in what they implement. Probe capabilities and degrade gracefully.
- **`422` carries field-level detail.** Validation failures return the FastAPI
  `HTTPValidationError` shape — `{"detail": [{loc, msg, type}, ...]}` — which tells you
  exactly which field of which row was wrong. Surface `loc` to the caller.
- **`400` means a malformed body, `401` means the deployment rejected your credential,
  `500` means the scorer itself failed.** Retry `500` with backoff; never retry `400` or
  `422` unchanged.
- **operationIds are FastAPI autogenerated** (`score_rows_model_score_post`), so generated
  SDK and MCP tool names from this spec will be awkward. Use them verbatim anyway — they are
  what the contract declares.
